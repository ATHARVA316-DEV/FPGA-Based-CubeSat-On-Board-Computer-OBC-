# FPGA-Based CubeSat On-Board Computer (OBC) 

**Duration:** 8 months
**Domain:** Embedded Systems / FPGA / Aerospace Electronics

---

## 1. Executive Summary

This project designs and implements a simplified CubeSat On-Board Computer (OBC) on an FPGA. The OBC performs the five core functions of a real satellite flight computer at reduced scope: sensor acquisition, data processing/storage, telemetry downlink, command uplink, and autonomous fault detection with safe-mode entry. A PC running a ground-station GUI stands in for the mission control station, communicating over UART/USB.

The design intentionally mirrors real OBC architecture (e.g., a hybrid processing-system + programmable-logic split, as used on Zynq-based flight computers) rather than being a toy demo, so the result is portfolio/publication-worthy and extensible toward a real CubeSat subsystem.

## 3. System Architecture

```
                         ┌───────────────────────────────────────────┐
                         │                  FPGA (OBC)                │
                         │                                             │
  Sensors ──I2C/SPI/ADC──▶  Sensor Interface  ──▶  Data Processing &   │
  (IMU, Temp, Light,     │      Modules            Formatting Unit     │
   Voltage/Current)      │        │                      │             │
                         │        ▼                      ▼             │
                         │   Fault Detection ◀──▶  Onboard Storage     │
                         │   & Watchdog FSM         (BRAM + SPI Flash) │
                         │        │                      │             │
                         │        ▼                      ▼             │
                         │   Safe-Mode Controller ─▶ Telemetry Packet  │
                         │        ▲                    Formatter       │
                         │        │                      │             │
                         │   Command Parser  ◀───────────┘             │
                         │        ▲                      │             │
                         │        └──────UART/USB─────────┘             │
                         └───────────────────────────────────────────┘
                                          │
                                          ▼
                          Ground Station PC (Python GUI)
                    Telemetry dashboard · Command console · Logs
```

**Design principle:** the FPGA fabric handles deterministic, timing-critical work (sensor sampling, watchdog, fault detection, framing) while a lightweight top-level FSM or soft-core handles sequencing/command dispatch — matching how real flight computers separate hard real-time logic from mission logic.

## 4. Functional Requirements

- **FR1** — Read at least 3 sensors: IMU (accel/gyro), temperature, light intensity, and optionally bus voltage/current (INA219-style) as a simulated power-subsystem telemetry point.
- **FR2** — Sample sensors on a fixed schedule (e.g., 1 Hz housekeeping, 10 Hz IMU) generated by an on-chip timer, not software polling delays.
- **FR3** — Store the last N telemetry frames in a circular buffer (BRAM) and persist a log to SPI flash/SD card.
- **FR4** — Format telemetry into fixed-length packets with a sync word, sequence counter, timestamp, payload, and checksum (CCSDS-inspired framing).
- **FR5** — Transmit telemetry over UART at a configurable rate; ground station decodes and displays it live.
- **FR6** — Accept uplinked commands (e.g., set sample rate, request stored log, force safe mode, reset fault flags) validated by checksum before execution.
- **FR7** — Monitor sensor values against configurable min/max bounds and a heartbeat/watchdog timer; on violation, autonomously transition to Safe Mode (reduced sampling, non-essential outputs disabled, fault beacon sent).
- **FR8** — Provide a manual recovery command to exit Safe Mode from the ground station.

## 5. Non-Functional Requirements

- Modular HDL (separate, independently testable modules per function).
- All modules simulated with self-checking testbenches before hardware bring-up.
- Fault-to-safe-mode latency documented and bounded (target: < 1 s).
- Design portable across at least two FPGA families conceptually (Xilinx primary).
- Full version control history (Git) and a wiring/test log.

## 6. Hardware Architecture

### 6.1 FPGA platform (recommendation)

| Option | Board | Why |
|---|---|---|
| **Primary** | Digilent **Zybo Z7-20** (Zynq-7020, PS+PL) | Programmable logic for deterministic sensor/fault handling; ARM Cortex-A9 PS available if you later want to run flight-software-style logic (e.g. µC/OS, or bare-metal C) alongside HDL — closest analogue to real OBC hardware (many real CubeSats use Zynq/RFSoC-class parts) |
| **Budget alt.** | Digilent **Basys 3** (Artix-7) + soft-core (PicoBlaze/MicroBlaze-lite) if a CPU is wanted | Cheaper, pure FPGA, still fully capable for this scope with everything done in HDL FSMs (no PS needed) |

Given your existing KiCad/embedded background, either is a reasonable jump into FPGA-land; Zybo is recommended if you want the PS-side to double as a mission-logic layer later.

### 6.2 Sensor suite

| Sensor | Interface | Role |
|---|---|---|
| MPU6050/9250 (IMU) | I2C | Attitude/vibration proxy |
| DS18B20 or LM35 | 1-Wire / ADC | Thermal housekeeping |
| BH1750 (light) | I2C | Sun-sensor proxy |
| INA219 (bus V/I) *(optional)* | I2C | Power-subsystem telemetry |

### 6.3 Storage & comms

- **BRAM** ring buffer for last-N frames (fast, volatile).
- **SPI flash module (W25Qxx)** or microSD (SPI mode) for persistent log — survives FPGA reconfiguration/reset.
- **UART over USB-UART bridge** (onboard FTDI/CP2104 on most dev boards) for the ground link — simplest reliable choice; CAN could be a stretch goal given your EV/Team Haya CAN experience, but isn't required for the core objective.

### 6.4 Optional custom carrier PCB

If a clean sensor breakout is wanted instead of jumper-wired modules, a small carrier PCB (I2C bus + connectors + status LEDs) is a natural KiCad task, matching your existing PCB workflow — proposed as a stretch item in Month 2, not on the critical path.

## 7. Firmware/HDL Architecture

Modules (Verilog/VHDL, one per block, each with its own testbench):

1. `i2c_master` / `spi_master` — sensor bus drivers
2. `sensor_scheduler` — timer-driven sampling FSM
3. `telemetry_formatter` — packetizer (sync + seq + timestamp + payload + CRC)
4. `storage_ctrl` — BRAM ring buffer + SPI flash writer
5. `uart_tx` / `uart_rx` — ground link
6. `command_parser` — decode + checksum-validate uplinked commands
7. `fault_monitor` — bounds checking + watchdog timer
8. `safe_mode_fsm` — top-level mode controller (NOMINAL ↔ SAFE), gates outputs
9. `top` — interconnects all of the above

---

## 8. Fault Detection & Safe Mode Strategy

**Detected fault classes:**
- Sensor out-of-range reading (stuck value, NaN-equivalent, bus timeout/NACK)
- Missed heartbeat / watchdog timeout (main FSM stall)
- Communication link loss (no valid uplink for X seconds)
- Storage write failure (flash busy/error flag)

**Safe Mode behavior:**
- Reduce sample rate to minimum housekeeping only
- Disable non-essential downlink content (send fault beacon instead of full telemetry)
- Log fault cause + timestamp to persistent storage
- Require explicit ground command to clear fault flag and resume NOMINAL

## 12. Verification & Test Plan

1. **Unit level:** self-checking testbench per HDL module (simulation only).
2. **Integration (bench):** each sensor bus verified individually on hardware before combining.
3. **Loopback test:** UART TX→RX loopback to validate framing/CRC before involving the GS PC.
4. **End-to-end telemetry test:** live sensor → packet → GS display, cross-checked against a known reference reading.
5. **Command test:** each supported command exercised and its effect verified on OBC state.
6. **Fault injection test:** deliberately disconnect a sensor / stall the FSM / kill the UART link and confirm Safe Mode entry within the target latency and correct logging.
7. **Endurance test:** 30+ minute continuous run with at least 2 injected faults and 1 recovery command.

## 14. Risk Assessment

| Risk | Impact | Mitigation |
|---|---|---|
| I2C bus contention/noise on breadboard wiring | Sensor read errors | Keep bus lines short, use proper pull-ups, test each sensor in isolation first |
| Timing closure issues in HDL as design grows | Build failures late in project | Keep clock domains simple, avoid unnecessary clock-domain crossings, timing-check after every major module addition |
| UART framing desync | Corrupted telemetry | Sync word + CRC + resync-on-error logic from the start (don't defer to Month 6) |
| Scope creep (adding CAN, RTOS, etc.) | Timeline slip | Treat anything beyond Section 4's FRs as explicit stretch goals only after core loop works |
| Flash/SD write reliability | Log data loss | Add write-verify + fallback to BRAM-only logging if persistent storage fails |
